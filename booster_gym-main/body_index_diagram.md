# 多Actor环境的刚体索引组织

## 刚体存储结构

在Isaac Gym中，当有多个actor时，刚体按照以下方式组织：

```
body_states 张量形状: [num_envs, total_bodies_per_env, 13]

每个环境的刚体排列:
┌─────────────────────────────────────────────────────┐
│ 环境 0                                              │
├─────────────────────────────────────────────────────┤
│ [0]  机器人躯干 (Trunk) ← self.base_indice 指向这里 │
│ [1]  机器人刚体1                                    │
│ [2]  机器人刚体2                                    │
│ ...                                                 │
│ [12] 机器人刚体12                                   │
├─────────────────────────────────────────────────────┤
│ [13] 足球场刚体0                                    │
│ [14] 足球场刚体1                                    │
│ [15] 足球场刚体2                                    │
├─────────────────────────────────────────────────────┤
│ [16] 足球刚体                                       │
└─────────────────────────────────────────────────────┘

环境 1: 相同的结构
环境 2: 相同的结构
...
环境 4095: 相同的结构
```

## 关键点

1. **`self.base_indice`** 是机器人资产内部的索引（0-12之间）
2. **机器人刚体总是从索引0开始**，因为它是第一个创建的actor
3. **每个环境的刚体排列顺序相同**

## 使用示例

```python
# 获取所有环境的机器人躯干状态
trunk_states = self.body_states[:, self.base_indice, :]  # 形状: [4096, 13]

# 在所有环境的机器人躯干上施加推力
self.pushing_forces[:, self.base_indice, :] = force_vector  # 形状: [4096, 3]

# 获取所有环境的足球状态（假设足球是索引16）
ball_body_states = self.body_states[:, 16, :]  # 形状: [4096, 13]
```

## 为什么这样设计是正确的？

1. Isaac Gym保证了actor创建顺序决定刚体存储顺序
2. 机器人总是第一个创建的actor（在代码第145行）
3. 所以机器人的刚体总是占据索引[0, num_robot_bodies)
4. `self.base_indice`作为机器人内部索引，正好对应到正确的位置
